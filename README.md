# 회의실 예약 시스템 - Frontend

사내 회의실 예약 업무를 웹으로 옮긴 서비스로, 달력·타임라인 UI로 예약 현황을 시각화하고 사용자와 관리자의 화면·라우팅을 역할별로 분리해 구현한 Next.js 프론트엔드입니다.

---

## 프로젝트 소개

오프라인/메신저로 처리되던 회의실 예약을 하나의 웹 화면에서 처리할 수 있도록 만든 예약 관리 시스템입니다. 단순 CRUD로 시작했지만, 실제 서비스 운영을 가정해 다음까지 범위를 넓혔습니다.

- 회의실별 예약 현황을 시간 단위로 보여주는 타임라인 UI
- 예약 생성/수정/취소 시 백엔드 검증 결과(시간 충돌, 취소된 예약 수정 불가 등)를 사용자에게 그대로 안내하는 예외 처리
- 일반 사용자와 관리자의 화면 및 라우팅을 구분하고, 사용자 역할에 따라 노출되는 기능과 메뉴를 분리한 구조
- Docker 기반 로컬 통합 실행 환경과 Vercel 배포 환경 구성

**주요 사용자 흐름**은 크게 두 갈래입니다.

1. 회의실 목록에서 원하는 방을 골라 → 날짜를 선택하고 → 타임라인에서 빈 시간을 드래그/클릭으로 선택해 → 예약을 신청하는 흐름
2. 특정 날짜·시간대가 이미 정해져 있을 때, 그 조건에 맞는 빈 회의실을 검색해 → 검색 결과에서 바로 예약하는 흐름

## 주요 기능

### 사용자
- 회원가입 / 로그인 / 로그아웃 (JWT 기반 인증)
- 회의실 목록 및 상세 조회
- 회의실 상세 화면의 달력 + 타임라인에서 드래그 또는 클릭으로 시간대를 선택해 예약 생성
- 날짜·시간 조건으로 빈 회의실 검색 후 바로 예약
- 내 예약 목록 조회 (전체 / 예약확정 / 취소됨 탭 필터)
- 예약 수정 (제목, 날짜, 시간 변경) 및 취소

### 관리자
- 관리자 대시보드 (전체 회의실 수, 오늘 예약 수, 전체 회원 수, 이번 달 예약 수 요약 + 오늘 예약 리스트)
- 회의실 등록 / 수정 / 삭제
- 전체 예약 현황 조회 (상태별 필터, 페이지네이션)
- 전체 회원 목록 조회 (권한 뱃지, 회원별 예약 수, 페이지네이션)
- 회의실별 예약 통계 (전체/이번 달 예약 수, 막대 그래프)

일반 사용자와 관리자는 로그인 응답의 `role` 값으로 구분되며, 관리자로 로그인하면 네비게이션 메뉴 자체가 사용자용 메뉴(내 예약, 빈 회의실 찾기) 대신 관리자용 메뉴로 바뀝니다.

## 주요 구현 내용

### 1. API 통신 구조

`src/lib/api.ts`에서 axios 인스턴스를 하나 만들고, 그 위에 도메인별 API 모듈(`authApi`, `roomsApi`, `reservationsApi`, `adminApi`)을 분리해 두었습니다. 화면 컴포넌트는 axios를 직접 다루지 않고 이 모듈만 호출합니다.

```ts
const api = axios.create({ baseURL: '/api' });
```

- **요청 인터셉터**: `localStorage`의 토큰을 읽어 모든 요청에 `Authorization: Bearer <token>` 헤더를 자동으로 붙입니다. 화면마다 인증 헤더를 신경 쓸 필요가 없습니다.
- **응답 인터셉터**: 401 응답을 받으면 저장된 토큰/사용자 정보를 지우고 로그인 페이지로 강제 이동시켜, 만료된 세션으로 계속 요청이 나가는 상황을 막습니다.
- baseURL을 절대 주소가 아닌 `/api`(같은 origin의 상대 경로)로 고정한 이유는 아래 "Backend 연동 구조"에서 설명합니다.

에러 처리는 컴포넌트 단에서 담당합니다. 단순 실패는 `alert`로 안내하지만, 예약 수정처럼 백엔드가 상황별 에러 코드(`RESERVATION_TIME_CONFLICT`, `RESERVATION_ALREADY_CANCELLED` 등)를 내려주는 API는 코드→한글 메시지 매핑 테이블을 두어 사용자에게 원인을 구체적으로 보여줍니다 (`src/app/reservations/page.tsx`의 `EDIT_ERROR_MESSAGES`).

### 2. 인증 흐름

- 로그인 성공 시 응답으로 받은 JWT와 사용자 정보(`username`, `role`)를 각각 `localStorage`(`token`, `user`)에 저장합니다.
- 인증이 필요한 페이지는 별도의 Next.js 미들웨어 없이, 각 페이지 컴포넌트의 `useEffect`에서 `isLoggedIn()` / `isAdmin()`(`src/lib/auth.ts`)을 확인해 조건에 맞지 않으면 `router.replace`로 리다이렉트합니다. 예를 들어 내 예약 페이지는 비로그인 시 `/auth/login`으로, 회의실 등록/수정 페이지는 비관리자일 때 `/rooms`로 보냅니다.
- 이후 모든 API 요청은 위 axios 인터셉터가 저장된 토큰을 자동으로 실어 보내므로, 화면 컴포넌트에서 별도로 인증 헤더를 구성하지 않습니다.
- 로그아웃은 저장된 토큰/사용자 정보를 지우고 로그인 페이지로 이동하는 단순한 동작이며, 서버 쪽 세션 무효화 없이 클라이언트 상태만 정리합니다.

### 3. 예약 UI/상태 처리

회의실 상세 페이지(`src/app/rooms/[id]/page.tsx`)는 09:00~22:00을 30분 단위(총 26칸)로 나눈 타임라인을 그리고, 선택한 날짜의 예약 현황을 조회해 각 칸을 비어있음/예약됨/선택됨 세 가지 상태로 표시합니다.

- **드래그와 클릭 두 가지 방식**으로 시간대를 선택할 수 있도록, `mousedown` ~ `mouseup` 사이에 `mouseenter`가 한 번이라도 발생했는지를 `useRef`로 추적해 드래그였는지 단순 클릭이었는지 구분합니다.
- 클릭만으로도 범위를 넓혀갈 수 있도록, 첫 클릭에서 anchor(기준 칸)를 저장해두고 이후 클릭 시 anchor 기준으로 범위를 재계산합니다.
- 한 번에 최대 3시간(6칸)까지만 선택되도록 범위를 계산 단계에서 제한하고, 오늘 날짜의 지난 시간대와 이미 예약된 칸은 선택 자체가 불가능하도록 막습니다.
- `/rooms/available` 페이지는 날짜(필수)와 시작/종료 시간(선택)으로 조건 검색을 하고, 검색 결과에서 바로 예약 모달을 열어 예약까지 이어지도록 했습니다. 시간을 입력하지 않고 검색한 경우에는 예약 모달 안에서 시작/종료 시간을 다시 선택하게 해, 검색 조건과 실제 예약 시간이 다를 수 있는 케이스를 흡수합니다.
- 예약 수정/취소는 `/reservations` 페이지에서 처리하며, 취소된 예약은 수정 버튼 자체가 노출되지 않도록 상태(`CONFIRMED`/`CANCELLED`)에 따라 UI를 분기합니다.

### 4. 관리자 기능

관리자 전용 페이지는 회의실 등록/수정처럼 사용자 페이지에 관리자 UI를 얹은 경우(`/rooms/new`, `/rooms/edit/[id]`)와, `/admin` 하위에 독립된 페이지로 존재하는 경우(대시보드, 전체 예약, 회원 목록, 통계)로 나뉩니다. 모든 관리자 페이지는 진입 시 `isAdmin()`을 확인해 통과하지 못하면 `/rooms`로 돌려보냅니다. 이는 화면 진입을 구분하는 클라이언트 측 라우팅 처리이며, 그 자체가 API 접근에 대한 보안을 보장하지는 않습니다.

- **대시보드**는 회의실 목록, 오늘 예약, 회원 수(페이지 크기 1로 조회해 `totalElements`만 사용), 회의실별 통계 API를 `Promise.all`로 병렬 조회해 요약 카드 4개와 오늘 예약 테이블을 구성합니다.
- **전체 예약/회원 목록**은 백엔드의 페이지네이션 API에서 초기 조회 시 필요한 데이터를 한 번에 가져온 뒤, 상태 필터·페이지 전환은 클라이언트에서 처리합니다. 현재 프로젝트의 데이터 규모와 사내 도구 성격을 고려한 선택이며, 대규모 데이터를 전제로 한 설계는 아닙니다.
- **통계 페이지**는 회의실별 이번 달 예약 수 중 최댓값을 기준으로 막대 길이(%)를 계산해 상대적인 이용률을 보여줍니다.

## Backend 연동 구조

**현재 구조**

```
사용자
  → Next.js (이 저장소)
  → /api/* 요청
  → Next.js rewrites (서버 사이드 프록시)
  → Backend API (API_SERVER_URL)
```

`next.config.ts`의 rewrites 설정이 이 구조의 핵심입니다.

```ts
async rewrites() {
  return [
    {
      source: "/api/:path*",
      destination: `${process.env.API_SERVER_URL}/api/:path*`,
    },
  ];
}
```

브라우저는 항상 같은 origin의 `/api/...`로만 요청을 보내고, 실제 백엔드 주소로의 전달은 Next.js 서버가 대신 수행합니다. 이전에는 `NEXT_PUBLIC_API_URL`을 클라이언트 번들에 그대로 노출해 사용했지만, 백엔드 서버 주소를 브라우저에 드러낼 이유가 없고 빌드 시점에 값이 고정된다는 문제도 있어 서버 전용 환경변수(`API_SERVER_URL`) + rewrites 프록시 방식으로 전환했습니다.

**배포 검증 당시 (AWS 인프라)**

AWS EC2 기반으로 실제 배포와 운영 검증까지 완료했으며, 현재는 비용 절감을 위해 AWS 인프라 운영을 종료한 상태입니다. 당시에는 `API_SERVER_URL`이 EC2 인스턴스를 가리켰고, 구조는 다음과 같았습니다.

```
사용자
  → Vercel (Next.js)
  → Next.js rewrites
  → AWS EC2 HTTP :80
  → Nginx → Spring Boot API
```

Nginx와 Spring Boot API는 별도의 백엔드 저장소에서 관리되며, rewrites 이후 구간(Nginx, Spring Boot API로의 라우팅)은 AWS 운영 당시의 백엔드 인프라 구성입니다.

## 실행 방법

### 로컬 실행

```bash
npm install
npm run dev
```

`http://localhost:3000` 접속. 그 외 사용 가능한 스크립트는 `npm run build`(프로덕션 빌드), `npm run start`(빌드 결과 실행), `npm run lint`(ESLint 검사)입니다.

### 환경변수

`.env.local` 파일에 아래 변수가 필요합니다. rewrites가 서버 사이드에서 값을 읽으므로 `NEXT_PUBLIC_` 접두사를 붙이지 않습니다.

```bash
# .env.local (예시, 민감한 실제 주소는 별도 관리)
API_SERVER_URL=http://localhost:8080
```

### Docker 실행

meeting-web과 meeting-api(백엔드) 컨테이너가 같은 external network(`meeting-network`)로 통신하므로, 최초 1회 아래 네트워크를 만들어야 합니다.

```bash
docker network create meeting-network
```

```bash
docker compose up --build
```

Docker 환경에서 `API_SERVER_URL`은 컨테이너 이름 기반 주소(`http://meeting-api:8080`)를 기본값으로 사용합니다(`docker-compose.yml`). 백엔드(meeting-api)가 같은 네트워크에서 먼저 실행되어 있어야 정상적으로 API 요청이 처리됩니다.

## 배포

- **Vercel**: 이 저장소를 Vercel에 연결해 배포하며, `API_SERVER_URL`을 Vercel 프로젝트 환경변수로 등록해 rewrites가 배포 환경에서도 백엔드로 요청을 프록시하도록 구성합니다.
- **Docker**: `Dockerfile`은 의존성 설치(`deps`) → 빌드(`builder`) → 실행(`runner`) 3단계 멀티스테이지로 구성되어 있고, `output: "standalone"` 설정으로 최소 구성의 실행 이미지를 만듭니다. 실행 컨테이너는 non-root 사용자(`nextjs`)로 구동됩니다.
